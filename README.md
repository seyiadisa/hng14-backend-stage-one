# Insighta Labs+

Insighta Labs+ is a production-oriented profile intelligence API for creating,
querying, searching, exporting, and bulk-ingesting demographic profile data. It
combines secure GitHub OAuth authentication, role-based access control,
deterministic query parsing, canonical query caching, PostgreSQL-backed
persistence, and chunked CSV ingestion for large operational datasets.

The system has evolved from a simple name-classification service into a
scalable backend application designed for concurrent web and CLI clients,
read-heavy traffic, remote database latency, and large CSV uploads.

## Live System

- Production API: `https://insighta-labs.fastapicloud.dev/`
- Frontend application: `https://insighta-lab.vercel.app/`
- Frontend repository: `https://github.com/seyiadisa/hng-insighta-web`
- CLI repository: `https://github.com/seyiadisa/hng-insighta-cli`

## Features

- GitHub OAuth login with access and refresh tokens stored in secure cookies.
- Role-based access control for `analyst` and `admin` users.
- CSRF protection for selected cookie-authenticated requests.
- Rate limiting for auth and profile endpoints.
- API version enforcement through the `X-API-Version: 1` header on profile routes.
- Request logging for method, endpoint, status code, and response time.
- Create a profile from a single `name` input.
- Call these public inference APIs:
  - `https://api.genderize.io?name={name}`
  - `https://api.agify.io?name={name}`
  - `https://api.nationalize.io?name={name}`
- Derive and store `gender`, `gender_probability`, `age`, `age_group`, `country_id`, `country_name`, and `country_probability`.
- Prevent duplicate profile creation for the same normalized name.
- List stored profiles with indexed filtering, stable sorting, and pagination.
- Search stored profiles with a deterministic rule-based natural language parser.
- Normalize equivalent filters into canonical cache keys before query execution.
- Cache successful repeated list/search queries with bounded in-process TTL caching.
- Export profile results as CSV.
- Upload large profile CSV files with streaming/chunked validation and PostgreSQL `COPY` ingestion.
- Include `country_name` in profile responses and CSV exports.
- Return profile timestamps in UTC ISO 8601 format with a `Z` suffix.
- Use UUID v7 IDs generated by the database.
- Tune PostgreSQL connection pooling for remote database workloads.
- Add composite profile indexes for common read-heavy query patterns.

## Setup

### 1. Clone the Repository

```bash
git clone <repository-url> insighta-labs
cd insighta-labs
```

### 2. Install Dependencies

This project uses `uv` and includes a lockfile:

```bash
uv sync --locked
```

### 3. Configure Environment Variables

Create a `.env` file in the project root:

```env
DATABASE_URL=postgresql+asyncpg://username:password@host:5432/database_name

GITHUB_CLIENT_ID=your_github_oauth_client_id
GITHUB_CLIENT_SECRET=your_github_oauth_client_secret
GITHUB_REDIRECT_URI=http://127.0.0.1:8000/auth/github/callback

FRONTEND_URL=http://localhost:3000
FRONTEND_REDIRECT_URI=http://localhost:3000/auth/callback

ACCESS_TOKEN_EXPIRE_MINUTES=15
REFRESH_TOKEN_EXPIRE_MINUTES=1440

JWT_SECRET_KEY=replace-with-a-long-random-secret
JWT_ALGORITHM=HS256
```

## Authentication and Request Requirements

Authentication starts with:

```text
GET /auth/github
```

GitHub redirects back to:

```text
GET /auth/github/callback
```

After a successful callback, the API sets:

- `access_token`
- `refresh_token`
- `csrf_token`

The GitHub OAuth flow also uses short-lived `github_oauth_state` and
`github_code_verifier` cookies during login.

Profile routes require:

- `X-API-Version: 1`
- an authenticated user, either through the `access_token` cookie or an `Authorization: Bearer <token>` header
- appropriate role access

Requests protected by CSRF also require:

```text
X-CSRF-Token: <csrf_token_cookie_value>
```

CSRF validation is enforced on:

- `POST /auth/refresh`
- `POST /auth/logout`
- `POST /api/profiles`
- `POST /api/profiles/upload`
- `GET /api/profiles/search`

Role access:

- `admin`: create, upload, and delete profiles
- `analyst` or `admin`: list, search, export, and fetch profiles

Default roles:

- new GitHub users are created as `analyst`

Rate limits:

- auth endpoints: `10/minute`
- profile endpoints: `60/minute`

### Upload Profiles from CSV

`POST /api/profiles/upload`

Requires `admin`, API version header, authentication, and CSRF validation.

Accepts a multipart form upload with the file field named `file`.

Required CSV columns:

```text
name,gender,gender_probability,age,country_id,country_probability
```

The upload path streams the file with Python's CSV reader, validates rows
independently, derives `age_group` and `country_name`, and skips bad rows
without failing the entire upload. Duplicate names follow the same idempotency
rule as `POST /api/profiles`.

Valid rows are processed in chunks of `5,000`. For each upload, the service
creates a unique short-lived PostgreSQL staging table, copies each validated
chunk into it with asyncpg `COPY`, then merges rows into `profiles` table
using `INSERT ... SELECT ... ON CONFLICT (name) DO NOTHING`. This avoids giant
`INSERT ... VALUES` statements and the PostgreSQL bind-parameter pressure that
large files can trigger.

Each chunk is committed independently. If processing fails midway, rows already
inserted remain in the database and a retry of the same file skips those names
as duplicates. The staging table is truncated between chunks and dropped at the
end of the upload. A small in-process semaphore limits concurrent uploads to
`2` so large imports do not exhaust the database pool.

Example success response:

```json
{
  "status": "success",
  "total_rows": 50000,
  "inserted": 48231,
  "skipped": 1769,
  "reasons": {
    "duplicate_name": 1203,
    "invalid_age": 312,
    "missing_fields": 254
  }
}
```

### List Profiles

`GET /api/profiles`

Requires `analyst` or `admin`, API version header, and authentication.

Supported query parameters:

- `gender`: `male` or `female`
- `age_group`: `child`, `teenager`, `adult`, or `senior`
- `country_id`: two-letter country code
- `min_age`: integer greater than or equal to `1`
- `max_age`: integer greater than or equal to `1`
- `min_gender_probability`: decimal from `0` to `1`
- `min_country_probability`: decimal from `0` to `1`
- `sort_by`: `age`, `created_at`, or `gender_probability`
- `order`: `asc` or `desc`
- `page`: integer greater than or equal to `1`, default `1`
- `limit`: integer from `1` to `50`, default `10`

Supported sorting fields:

- `age`
- `created_at`
- `gender_probability`

Supported sort order:

- `asc`
- `desc`

If `order` is provided, `sort_by` must also be provided. If both `min_age` and
`max_age` are provided, `min_age` cannot be greater than `max_age`.

Example:

```text
/api/profiles?gender=male&country_id=NG&sort_by=age&order=desc&page=1&limit=10
```

### Search Profiles with Natural Language

Requires `analyst` or `admin`, API version header, authentication, and CSRF validation.

Supported query parameters:

- `limit`: integer from `1` to `50`, default `10`

## Classification Rules

- `0-12` -> `child`
- `13-19` -> `teenager`
- `20-59` -> `adult`
- `60+` -> `senior`

For nationality, the API stores the highest-probability country returned by Nationalize.

## Natural Language Parsing

The natural language search in `GET /api/profiles/search` is rule-based. It converts a plain English query into the same structured filters used by `GET /api/profiles`.

### Gender Keywords

- `male`
- `males`
- `man`
- `men`
- `female`
- `females`
- `woman`
- `women`

If exactly one unique gender is found, that gender is used. If both male and female appear, no gender filter is applied.

### Age Group Keywords

- `child`
- `children` -> `child`
- `teenager`
- `teenagers` -> `teenager`
- `adult`
- `adults` -> `adult`
- `senior`
- `seniors` -> `senior`

If multiple age-group keywords appear, the last one wins.

### Age Range Keywords

- `young` -> `min_age=16`, `max_age=24`
- `above 30` -> `min_age=30`
- `over 30` -> `min_age=30`
- `older than 30` -> `min_age=30`
- `below 18` -> `max_age=18`
- `under 18` -> `max_age=18`
- `younger than 18` -> `max_age=18`
- `between ages 20 and 45` -> `min_age=20`, `max_age=45`
- `aged 20-45` -> `min_age=20`, `max_age=45`
- `ages 20 to 45` -> `min_age=20`, `max_age=45`

### Country Keywords

Country extraction supports `from ...`, `living in ...`, and `in ...` phrases,
then matches the country phrase with `pycountry`. It also recognizes a small set
of deterministic country aliases and demonyms.

Supported aliases include:

- `nigerian` -> `Nigeria`
- `kenyan` -> `Kenya`
- `ghanaian` -> `Ghana`
- `angolan` -> `Angola`
- `canadian` -> `Canada`
- `south african` -> `South Africa`
- `uk`, `britain`, `british` -> `United Kingdom`
- `usa`, `us`, `america`, `american` -> `United States`

Example mappings:

- `young males` -> `gender=male`, `min_age=16`, `max_age=24`
- `females above 30` -> `gender=female`, `min_age=30`
- `women aged 20-45 living in Nigeria` -> `gender=female`, `min_age=20`, `max_age=45`, `country_id=NG`
- `Nigerian females between ages 20 and 45` -> `gender=female`, `min_age=20`, `max_age=45`, `country_id=NG`
- `people from angola` -> `country_id=AO`
- `adult males from kenya` -> `gender=male`, `age_group=adult`, `country_id=KE`
- `male and female teenagers above 17` -> `age_group=teenager`, `min_age=17`

- `missing_fields`
- `invalid_age`
- `invalid_gender`
- `invalid_probability`
- `invalid_country`
- `duplicate_name`
- `malformed_row`

## External API Validation Rules

The service does not store a profile when any upstream API returns invalid data.

- Genderize must return:
  - non-null `gender`
  - non-zero `count`
  - non-null `probability`
- Agify must return:
  - non-null `age`
- Nationalize must return:
  - a non-empty `country` list
  - a top country containing both `country_id` and `probability`

If any of these validations fail, the API responds with `502 Bad Gateway`.

## Persistence and Configuration

- The database URL is loaded from `.env` through `DATABASE_URL`.
- SQLAlchemy tables are created automatically when the app starts.
- Composite profile indexes are created on startup when missing.
- The app uses `asyncpg` and expects a PostgreSQL connection string.
- Profile and user IDs use PostgreSQL `uuidv7()` as their server-side default.
- Refresh tokens are stored as SHA-256 hashes in the database.
- The SQLAlchemy engine is configured with:
  - `echo=False`
  - `pool_size=10`
  - `max_overflow=20`
  - `pool_timeout=30`
  - `pool_pre_ping=True`
  - `pool_recycle=1800`

## Query Performance and Cache

Profile list and search requests use a shared query execution path with stable
ordering and composite indexes for common filters. Equivalent structured filters
are converted into a canonical form before cache lookup so repeated list/search
requests avoid redundant database work.

The in-process query cache is intentionally bounded:

- TTL: `60` seconds
- max entries: `512`
- cached endpoints: `GET /api/profiles` and `GET /api/profiles/search`
- invalidated after profile create, successful CSV upload chunks, and profile delete

CSV export is not cached because it returns a downloadable file response.

## Example cURL Requests

## Notes

- Names are normalized before storage by trimming whitespace and converting to lowercase.
- The list and search endpoints both return paginated responses with `page`, `limit`, `total`, `total_pages`, `links`, and `data`.
- CSV uploads stream rows, copy valid chunks through a per-upload staging table, and commit each successful chunk independently.
- Query validation errors return `422` with the message `Invalid query parameters`.
- Body validation errors return `422` with the message `Invalid type`.
- Unhandled exceptions return `500` with the message `Internal server error`.
