# Name Profile Classification API

A FastAPI service that accepts a person's name, calls external inference APIs, stores the resulting profile, and exposes endpoints to create, list, search, fetch, and delete profiles.

This project was built for the HNG Stage One backend task.

## Features

- Create a profile from a single `name` input.
- Call these public inference APIs:
  - `https://api.genderize.io?name={name}`
  - `https://api.agify.io?name={name}`
  - `https://api.nationalize.io?name={name}`
- Derive and store:
  - `gender`
  - `gender_probability`
  - `age`
  - `age_group`
  - `country_id`
  - `country_probability`
- Prevent duplicate profile creation for the same normalized name.
- List stored profiles with filtering, sorting, and pagination.
- Search stored profiles with a rule-based natural language parser.
- Return timestamps in UTC ISO 8601 format with a `Z` suffix.
- Use UUID v7 IDs generated by the database.

## Classification Rules

- `0-12` -> `child`
- `13-19` -> `teenager`
- `20-59` -> `adult`
- `60+` -> `senior`

For nationality, the API stores the highest-probability country returned by Nationalize.

## Natural Language Parsing Approach

The natural language search in `GET /api/profiles/search` is rule-based. It does not use AI, embeddings, or an LLM. Instead, it converts a plain English query into the same structured filters used by `GET /api/profiles`.

### Step 1. Normalize the query

The parser:

- converts the query to lowercase
- removes punctuation by replacing non-alphanumeric characters with spaces
- splits the text into words

Example:

```text
"Young Males from NIGERIA!!!"
```

becomes:

```text
"young males from nigeria"
```

### Step 2. Extract supported filter signals

The parser currently supports these categories.

#### Gender keywords

These map to the `gender` filter:

- `male`
- `males`
- `female`
- `females`

Behavior:

- if exactly one unique gender is found, that gender is used
- if both male and female appear, no gender filter is applied

#### Age group keywords

These map to the stored `age_group` filter:

- `child`
- `children` -> `child`
- `teenager`
- `teenagers` -> `teenager`
- `adult`
- `adults` -> `adult`
- `senior`
- `seniors` -> `senior`

Behavior:

- age-group matches preserve order
- if multiple age-group keywords appear, the last one wins

Example:

- `adult senior males` -> `age_group=senior`

#### Age range keywords

These map to `min_age` and `max_age`:

- `young` -> `min_age=16`, `max_age=24`
- `above 30` -> `min_age=30`
- `over 30` -> `min_age=30`
- `older than 30` -> `min_age=30`
- `below 18` -> `max_age=18`
- `under 18` -> `max_age=18`
- `younger than 18` -> `max_age=18`

Note:

- `young` is only a parsing shortcut
- it does not map to a stored `age_group`

#### Country keywords

Country extraction looks for a `from ...` phrase.

Examples:

- `from nigeria`
- `from kenya`
- `from united states`
- `from uk`

How it works:

- the parser finds the word `from`
- it collects following words until it reaches a stop word like `male`, `female`, `adult`, `young`, or `above`
- it joins those words into a country phrase
- it normalizes common aliases before matching with `pycountry`

Supported aliases currently include:

- `nigerian` -> `Nigeria`
- `kenyan` -> `Kenya`
- `ghanaian` -> `Ghana`
- `angolan` -> `Angola`
- `canadian` -> `Canada`
- `south african` -> `South Africa`
- `uk`, `britain`, `british` -> `United Kingdom`
- `usa`, `us`, `america`, `american` -> `United States`

The matched country is converted to its ISO alpha-2 code and applied as `country_id`.

### Step 3. Build structured filters

After parsing, the natural-language route creates a `ProfileListQueryParams` object containing only the supported derived filters:

- `gender`
- `age_group`
- `country_id`
- `min_age`
- `max_age`

It then reuses the same `apply_filters()` function as the regular list endpoint, so both routes use the same database filtering behavior.

### Example Mappings

- `young males` -> `gender=male`, `min_age=16`, `max_age=24`
- `females above 30` -> `gender=female`, `min_age=30`
- `people from angola` -> `country_id=AO`
- `adult males from kenya` -> `gender=male`, `age_group=adult`, `country_id=KE`
- `male and female teenagers above 17` -> `age_group=teenager`, `min_age=17`

## Limitations and Edge Cases

The parser is intentionally simple and rule-based. It works for the supported patterns above, but it does not try to understand unrestricted natural language.

Current limitations:

- It only understands a small fixed set of keywords and phrase patterns.
- Country parsing depends on phrases that include `from`.
- It does not support free-form country mentions without `from`, such as `nigerian males` unless the nationality word is inside a detected country phrase.
- It does not support compound logic such as `male or female`, `not male`, or grouped conditions.
- It does not support relative age language like `mid twenties`, `older adults`, or `late teens`.
- It does not support exact-age phrases like `age 25` or ranges written as `between 20 and 30`.
- It does not support multiple country filters in one query.
- It does not apply sorting from the search endpoint; search only supports `q`, `page`, and `limit`.
- If both `young` and another minimum-age phrase like `above 30` are present, the explicit numeric minimum-age phrase overrides the `young` minimum.
- If multiple age-group keywords appear, the last one is used instead of reporting ambiguity.
- If both genders appear, the parser drops the gender filter instead of raising an error.
- If no supported filter can be derived from `q`, the API returns:

```json
{
  "status": "error",
  "message": "Unable to interpret query"
}
```

Some edge cases intentionally left out:

- fuzzy typo correction such as `nigeira`
- synonyms outside the hardcoded set such as `ladies`, `guys`, `elders`, or `youths`
- comparisons like `at least 30`, `not more than 18`, or `30+`
- nested or conversational queries like `show me young males who are probably from nigeria`

## Error Responses

All errors follow this structure:

```json
{
  "status": "error",
  "message": "<error message>"
}
```

Common errors:

- `400 Bad Request` -> `Missing or empty name`
- `400 Bad Request` -> `Unable to interpret query`
- `404 Not Found` -> `Profile not found`
- `404 Not Found` -> `No profiles found matching the criteria`
- `422 Unprocessable Entity` -> `Invalid query parameters`
- `500 Internal Server Error` -> `Internal server error`
- `502 Bad Gateway` -> `${externalApi} returned an invalid response`

## External API Validation Rules

The service does not store a profile when any upstream API returns invalid data.

- Genderize must return:
  - non-null `gender`
  - non-zero `count`
  - non-null `probability`
- Agify must return:
  - non-null `age`
- Nationalize must return:
  - a non-empty `country` list
  - a top country containing both `country_id` and `probability`

If any of these validations fail, the API responds with `502 Bad Gateway`.

## Persistence and Configuration

- The database URL is loaded from `.env` through `DATABASE_URL`.
- SQLAlchemy tables are created automatically when the app starts.
- The app uses `asyncpg` and expects a PostgreSQL connection string.

  - `echo=True`

## Example cURL Requests

Create a profile:

```bash
curl -X POST "http://127.0.0.1:8000/api/profiles" \
  -H "Content-Type: application/json" \
  -d "{\"name\":\"ella\"}"
```

List profiles with pagination:

```bash
curl "http://127.0.0.1:8000/api/profiles?page=1&limit=10"
```

Filter and sort profiles:

```bash
curl "http://127.0.0.1:8000/api/profiles?gender=female&country_id=US&age_group=adult&sort_by=age&order=desc"
```

Search profiles with natural language:

```bash
curl "http://127.0.0.1:8000/api/profiles/search?q=young males from nigeria&page=1&limit=10"
```

Get one profile:

```bash
curl "http://127.0.0.1:8000/api/profiles/<profile-id>"
```

Delete a profile:

```bash
curl -X DELETE "http://127.0.0.1:8000/api/profiles/<profile-id>"
```

## Notes

- Names are normalized before storage by trimming whitespace and converting to lowercase.
- The list and search endpoints both return paginated responses with `page`, `limit`, and `total`.
- Query validation errors return `422` with the message `Invalid query parameters`.
- Unhandled exceptions return `500` with the message `Internal server error`.
